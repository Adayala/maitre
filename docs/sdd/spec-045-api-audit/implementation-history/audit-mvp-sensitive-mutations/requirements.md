## ADDED Requirements

### Requirement: Complete sensitive mutation coverage

Every state-changing operation in the MVP Floor, Ordering, Kitchen and Cash domains MUST declare
an audit policy and produce evidence for its terminal outcome. The policy SHALL use stable business
action codes and identify the tenant, applicable branch, actor, resource, request and correlation.

#### Scenario: Successful operational transition

- **WHEN** an authorized user completes a covered state transition
- **THEN** exactly one audit record identifies the business action, resource, actor and `SUCCEEDED`
  outcome
- **AND** the record uses the same tenant, branch and correlation context as the mutation

#### Scenario: Sensitive mutation has no policy

- **WHEN** a state-changing route or command is added to a covered domain without an audit policy
- **THEN** the audit coverage gate fails
- **AND** the change cannot pass required CI

### Requirement: Atomic success evidence

A successful covered mutation and its required audit record MUST commit in the same PostgreSQL
transaction together with any required outbox record. A mutation SHALL NOT become visible when its
success evidence cannot be persisted.

#### Scenario: Audit persistence fails

- **WHEN** audit persistence fails before a covered business transaction commits
- **THEN** the business state and related outbox writes are rolled back
- **AND** the API returns a sanitized failure with the request correlation ID

#### Scenario: Idempotent replay

- **WHEN** the same idempotent mutation is replayed with the same key and payload
- **THEN** the original result is returned
- **AND** no duplicate success audit fact is appended

### Requirement: Denied and failed attempt evidence

Authorization denials and domain failures for configured high-risk operations MUST produce an
audit record with `DENIED` or `FAILED`, a stable reason code and sanitized target information.
Failure to append non-transactional attempt evidence MUST be logged, metered and alerted.

#### Scenario: Unauthorized monetary action

- **WHEN** a user attempts to void a cash movement without the required permission
- **THEN** the mutation is denied
- **AND** audit evidence identifies the actor, tenant, branch, target, action and denial reason
  without revealing whether an out-of-scope resource exists

### Requirement: Safe bounded audit evidence

Audit state and diffs MUST be generated by resource-specific allowlist projectors. Records MUST
exclude credentials, authentication material, card data and unbounded request payloads, and MUST
enforce a serialized size limit.

#### Scenario: Mutation contains sensitive input

- **WHEN** a covered mutation receives a secret, payment credential or operator note
- **THEN** only allowlisted operational fields and a bounded sanitized note reach the audit store
- **AND** redaction tests prove the prohibited values are absent

### Requirement: Isolated audit discovery

Authorized audit readers SHALL query evidence by tenant and permitted branch scope, with optional
filters for action code, outcome, resource, actor, correlation and time range. Results MUST use
stable cursor pagination and MUST NOT expose evidence from another tenant or branch.

#### Scenario: Branch-scoped audit reader

- **WHEN** a reader scoped to one branch queries audit records
- **THEN** only records for that branch and tenant are returned
- **AND** tenant-wide records are returned only when the reader has the corresponding permission
